# Локальные LLM для бухгалтерских документов на Mac mini M4 16 ГБ — план исследования

Версия плана: **2** (2026-11-10). Учтены ответы владельца. Изменения против v1 — в конце файла.

**Железо:** Mac mini M4 (10 CPU / 10 GPU), 16 ГБ unified memory (≈12 ГБ доступно GPU по умолчанию), 120 ГБ/с, SSD 256 ГБ (≈196 ГБ свободно), macOS 26.3.1.

**Принципы:**
- только **open-source документы** с готовой разметкой;
- публикуем **только замеры и выводы**, сами документы не публикуем;
- всё работает **локально** на этом Mac.

---

## 1. Цель и вопросы исследования

Найти **максимально точную** конфигурацию для извлечения данных из бухгалтерских документов на 16 ГБ Mac mini и описать её цену: время, память, энергию. Отдельно — как результат зависит от **языка документа**.

- **RQ1. Точность.** Какая модель и какой конвейер дают лучшую точность по полям?
- **RQ2. Галлюцинации.** Как часто модель выдумывает значение отсутствующего поля? Как это зависит от модели, квантования, промпта и строгого JSON?
- **RQ3. Языки.** Насколько падает точность и растут галлюцинации на немецком, французском, итальянском, испанском, португальском, польском, нидерландском, китайском, японском, корейском и других языках по сравнению с английским? Какая модель лучшая для каждого языка?
- **RQ4. Тип документа.** Счета, чеки, банковские выписки, финансовые отчёты, e-счета со строками — где модели сильны и где ломаются?
- **RQ5. Скорость и ресурсы.** Секунды, память и энергия на документ. Парето-фронт «точность ↔ время».
- **RQ6. Как выжать максимум.** Голосование нескольких прогонов, второй проход-проверка, текстовый слой PDF, арифметические проверки — какой прирост точности и за какое время?

**Наш зазор (перепроверить в фазе 0):**
1. **Многоязычный бухгалтерский бенчмарк** локальных моделей: 10+ языков и несколько типов документов на одной методике. В найденных работах есть максимум EN + ZH.
2. **Контролируемые отсутствующие поля на реальных документах:** закрашиваем поле по его координатам из разметки и меряем, выдумает ли модель значение. Плюс влияние квантования, промпта и строгого JSON на эту частоту.
3. **Потребительский Apple silicon 16 ГБ:** точность вместе с временем, памятью и энергией на документ.
4. **Три подхода на одной машине:** VLM напрямую · OCR → текстовая LLM (база — встроенный OCR macOS) · специализированный экстрактор.

### 3.2. Правила достаточности и что из них следует

1. **Клетка «язык × тип»** показывается от 30 независимых документов, цель — 80. id (48) и ko (30) — с широкой
   погрешностью.
2. **Сравнение языков** — на блоке EuroDocBench: 8 языков, одни и те же 5 макетов, тип — счёт. Правило «у каждого
   языка два типа документов» снято: одинаковые макеты отделяют язык от типа лучше.
3. **Шрифт.** У fr в EuroDocBench нет моноширинного шрифта (такие счета исключены из-за дефекта глифа). Сравнение
   языков делается дважды: все 8 языков на документах без моноширинного шрифта и 7 языков (без fr) на всех.
   Макет и шрифт — колонка `template` в `final/manifest.csv`.
4. **Реальные документы.** Выводы «на реальных документах» — только для en (чеки), de и pt (счета), id и ko (чеки).
   Для fr, it, es, nl, pl есть только сгенерированные документы; это ограничение исследования, дальше не ищем.
   Результаты по сгенерированным и реальным документам показываются раздельно.
5. **Выдуманные ответы (правильный ответ null).** Основной замер — по блоку EuroDocBench целиком (около 400 null).
   По отдельным языкам — только как ориентир; порог 150 null проходят de и en. Для id (6 null) и ko (0) не считаем.
   В синтетических чеках ЕС subtotal не печатается и всегда null — показывать по полям, а не одной суммой.
6. **Банковские выписки** (8 документов) — вне выводов первого круга.
7. **Объём.** 1574 документа ≈ 13 часов на одну модель с одним промптом при 30 с на документ. Первый круг — на
   подвыборке; какой, решается при сборке конвейера.

### 3.3. Отсутствующие поля

- `null` в ответах — только подтверждённые просмотром страницы или доказанные кодом генератора и отсутствием в
  тексте страницы.
- 41 документ с закрашенным значением при оставленной подписи («IBAN: ____»); правильный ответ — `null`.

Стартовый список взят из калькулятора fidenubi.com. Его прогнозы памяти и скорости **сверяем с реальными замерами** (полезно и для сайта).

| Группа | Модели |
|---|---|
| **A. Универсальные VLM** (картинка → JSON) | Qwen3-VL 4B/8B · Qwen3.5 4B/9B · Gemma 4 E4B/12B · если запустятся: MiniCPM-V 4.5 8B, InternVL3.5 8B, GLM-4.1V 9B |
| **B. Экстракторы** | lift 9B (Datalab) · NuExtract3 4B (NuMind) |
| **C. OCR для конвейера** | Apple Vision OCR (встроен в macOS) · GLM-OCR 1.3B · PaddleOCR-VL 0.9B · DeepSeek-OCR small · текстовый слой PDF |
| **D. Текстовые LLM для конвейера** | Qwen3.5 9B · Gemma 4 12B · Llama 3.1 8B |
| **E. Стресс-трек «максимум»** | Qwen3.8 27B (VLM, авг. 2026; добавлена 2026-11-13) · Qwen3.6 27B и 35B-A3B в 2–3 бит · Bonsai 2 27B (тернарная) · с поднятым лимитом GPU-памяти |

Оценка памяти Qwen3.8 27B (до замера): 3 бит ≈ 11,5–12 ГБ весов + энкодер картинки и кэш ≈ 1–1,5 ГБ → 12,5–13,5 ГБ: только с поднятым `iogpu.wired_limit_mb`, на грани, возможен своп. 2 бит ≈ 8,5–9,5 ГБ: помещается в штатный лимит (~10,7 ГБ). Сначала smoke (33 документа, P1b) в 3 бит; при свопе или падениях — 2 бит. «Думание» выключить шаблоном и проверить по первым ответам. Готовых MLX-весов 2/3 бит может не быть — тогда квантовать самим (mlx-vlm convert; bf16 ≈ 54 ГБ на SSD).

**Квантование** для 2–3 финалистов: 4 / 6 / 8 бит.

**Облачные модели не используются** (решение владельца). Исследуем только локальные модели на этом Mac.

## 5. Как проверяем (протокол)

**Задачи:**
1. **Извлечение по схеме.** Единая JSON-схема для каждого типа документа:
   - счёт: продавец, покупатель, налоговые ID, номер, даты, валюта, нетто, НДС, итого, IBAN, строки;
   - чек: магазин, дата, позиции, итого, налог;
   - выписка: счёт, период, остатки, транзакции;
   - финотчёт: заданные показатели.
2. **Точечные вопросы**, в том числе по отсутствующим полям. Правильный ответ для них — `null`.

**Факторы:**

| Фактор | Уровни |
|---|---|
| Модель | раздел 4 |
| Язык и тип документа | раздел 3 |
| Конвейер | VLM напрямую · OCR → LLM · экстрактор · гибрид (картинка + текстовый слой) |
| Квантование | 4 / 6 / 8 бит (для финалистов) |
| Промпт | P0 нейтральный · P1 «верни null, если поля нет» · P2 + обязательная цитата из документа |
| Вывод | свободный JSON · constrained decoding по схеме |
| Язык промпта | английский · язык документа (для финалистов) |
| Ускорители | голосование 3 прогонов · второй проход-проверка · арифметический валидатор + повтор |

Полный перебор невозможен. Поэтому: пилот → 3–4 финалиста → факторы промпта, квантования и вывода только на финалистах.

**Правила:**
- temperature 0, фиксированный seed; на 10% выборки 3 повтора для оценки разброса.
- Нормализация перед сравнением: даты → ISO, суммы → decimal с учётом локальных форматов (`1.234,56` / `1 234,56` / `1,234.56`), ID без пробелов, Unicode NFKC для CJK.
- Одинаковые входы, схемы и промпты для всех моделей; всё версионируется в `protocol/`.
- Перед серией фиксируем окружение: версии, ревизии весов, `pmset`, отсутствие посторонней нагрузки.
- Прогоны идут непрерывно, в фоне, под `caffeinate`. Каждый ответ сразу пишется в JSONL, поэтому прогон продолжается после сбоя.
- Во время замеров скорости на Mac не запускаем ничего тяжёлого, иначе цифры времени исказятся. Если нагрузка была, это отмечается в журнале и прогон повторяется.

## 6. Метрики

**Точность:** field accuracy и F1 после нормализации (null по правилам ExtractBench) · ANLS для строк · доля документов, где верны все поля · F1 по строкам счёта (Венгерское сопоставление).

**Галлюцинации:**
- **False-fill rate** — доля отсутствующих полей, получивших значение. Главная метрика.
- **Over-abstention** — доля присутствующих полей, на которые модель ответила `null`.
- **Wrong-value rate** — поле есть, значение неверное.
- **Unsupported value** — значения нет в тексте документа.
- **Arithmetic violation** — не сходятся строки, нетто + НДС, итог.
- Для P2: доля цитат, реально найденных в документе.

**Скорость и ресурсы:** секунды на документ · кодирование картинки · prefill/decode tok/s · время до первого токена · документов в час · пиковая память и swap · **энергия на документ** (`powermetrics`) · троттлинг на длинных прогонах · холодный и тёплый старт.

**Надёжность:** доля валидного JSON · соответствие схеме · падения и OOM.

**Статистика:** 95% доверительные интервалы bootstrap; сравнение моделей парным тестом Макнемара. «A лучше B» пишем только при значимой разнице.

**Итог:**
- таблица «лучшая модель для каждого языка» и «для каждого типа документа»;
- Парето-графики «точность × время» и «точность × false-fill»;
- рекомендованная конфигурация для 16 ГБ.

```
Исследования/local-llm-accounting/
├── 00-plan.md            ← этот файл
├── 01-literature.md      ← работы, ссылки, зазор
├── journal.md            ← журнал: дата, что сделано, результат
├── final/                ← набор: страницы, ответы, состав, исключения, лицензии (README.md)
├── protocol/             ← схемы, промпты P0–P2, названия полей
├── harness/              ← runner.py (mlx-vlm), run.py (прогон), score.py + normalize.py (оценка), report.py
├── tools/fetch.py        ← скачивание источников (data/sources.yaml, data/manifest.json)
├── tests/                ← тесты оценки
├── runs/<run_id>/        ← config.json, predictions.jsonl, fields.csv, summary.md
├── models_cache/         ← веса моделей (не в git)
└── reports/              ← проверки набора, каталог моделей, отчёты
```

Прогон: `uv run python -m harness.run --model <repo> --revision <sha> --prompt P1 [--where lang=fr]`;
оценка: `uv run python -m harness.report runs/<run_id>`. Прогон продолжается с места остановки.

- Папка — локальный **git-репозиторий**, каждая серия — коммит. Любой прогон повторяется командой из его `config.json`.
- Python через `uv` с lock-файлом, версии рантаймов зафиксированы.
- Документация пишется по ходу, после каждого шага — запись в `journal.md`.
- **Рантайм:** основной — MLX / mlx-vlm; контрольный — llama.cpp (GGUF, constrained grammar). Ollama для замеров не используем: лишний слой, хуже контроль параметров.
- **Публикуемый пакет:** код, протокол, manifest (ссылки + sha256 вместо документов), сырые ответы моделей (без изображений) и метрики. По нему любой может повторить исследование, скачав наборы сам.

## 8. Фазы и сроки

### 8.1. Режим работы: «всё подготовить → один запуск → результаты»

Решение владельца: сначала полностью готовим всё (фазы 0–2), затем **один запуск** конвейера, который сам выполняет фазы 3–6 до готовых таблиц и графиков.

- **Очередь экспериментов** — один файл `study.yaml`: наборы, модели, факторы, порядок.
- **Пре-регистрация правил отбора** до старта, в `protocol/preregistration.md`. Например: «в основные прогоны идут 3 лучшие модели пилота по F1 при доле валидного JSON ≥ 90%; при равенстве — меньше false-fill». Конвейер применяет правила сам, без ручного вмешательства.
- **Модели по очереди:** скачать → проверить хэш → прогнать → записать результат → удалить. Пиковый расход диска — 1–2 модели.
- **Самозащита:** модель, которая не загрузилась или упала с OOM, пропускается с записью причины. Прогон останавливается, если доля валидного JSON < 50% или точность ≈ 0 на первых 20 документах (вероятная ошибка конфигурации). После сбоя или перезагрузки конвейер продолжает с места остановки.
- **Статус** в `runs/STATUS.md` обновляется по ходу: что сделано, что идёт, оценка оставшегося времени.
- **Рекомендованная (не обязательная) проверка** через 1–2 часа после старта, когда пройдёт smoke-тест.
- **Каркас многоразовый:** код в `harness/` не зависит от исследования. Новое исследование — новый `study.yaml` и, при необходимости, новый набор данных или схема.

### 8.2. Фазы и сроки

| Фаза | Содержание | Время |
|---|---|---|
| 0 | Добор литературы, подтверждение зазора | 0,5 дня |
| 1 | Установка окружения, smoke-тест моделей, замер памяти против калькулятора | 0,5–1 день |
| 2 | Загрузка наборов, маскирование, схемы, промпты, скорер с тестами | 1,5–2 дня |
| 3 | Пилот ≈70 документов × все кандидаты → финалисты | ≈0,5–1 сутки машинного времени |
| 4 | Основные прогоны: финалисты × языки × конвейеры × промпты × квантование | ≈3–4 суток непрерывно |
| 5 | Трек «максимум» + стресс-трек больших моделей | ≈1–2 суток |
| 6 | Анализ, отчёт, тексты по языкам | 1–2 дня (идёт параллельно с прогонами) |

**Итого ≈ 7–10 дней** по календарю. Из них подготовка — 2–3 дня, остальное время Mac считает 24/7.

Откуда цифра: один проход одной модели по 600 документам при 20–40 с на документ — 3–7 часов. Нужно 20–30 проходов, то есть ≈4–6 суток машинного времени.

Первые результаты (финалисты, первые цифры по языкам) — **на 3–4-й день**. Срок можно сократить, если уменьшить набор или число факторов.

## 9. Совместимость с подготовкой Mac к аренде

- Установка инструментов (Xcode CLT, Homebrew, Python/uv, mlx-vlm, llama.cpp) **не затрагивает** SSH, Screen Sharing, сеть и питание. Шаги из `Rent Preparing` можно делать параллельно.
- Во время прогонов Mac загружен почти на 100%. SSH и Screen Sharing продолжают работать, но медленнее.
- Перезагрузки, тест отключения питания и смену сети согласовываем, чтобы не оборвать прогон. Прогон продолжится с места остановки, но время потеряется.
- **Диск:** модели займут 80–120 ГБ из 196 ГБ. Модели, которые уже отыграли, удаляем.
- **Перед сдачей в аренду** — полный сброс Mac (он и так в процедуре). Исследование нужно закончить и выгрузить результаты до этого.

## 10. Доступ sudo

Нужен для двух вещей: `powermetrics` (энергия) и `sysctl iogpu.wired_limit_mb` (лимит GPU-памяти для стресс-трека).

**Пароль в чат не передавать.** Безопаснее выдать узкое правило: владелец один раз создаёт файл `/etc/sudoers.d/` с разрешением без пароля **только для этих двух команд**. Перед арендой правило удаляется. Точный текст правила подготовлю на утверждение.

## 11. Лицензии и публикация

Публикуем только замеры и выводы, документы не публикуем и не продаём (решение владельца). Наборы с пометкой non-commercial (EPHOIE, FUNSD, возможно XFUND) используем наравне с остальными. В отчёте для каждого набора указываем источник и лицензию, как требует атрибуция.
