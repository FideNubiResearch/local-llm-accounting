# Финальный набор документов

Документы, на которых тестируются модели, и правильные ответы к ним. В эксперименте используется только эта папка.
Набор заморожен: он не пересобирается, а меняется только осознанной правкой с записью в журнале.

## Состав

1572 документа: 865 счетов, 699 чеков, 8 банковских выписок; 10 языков (en 339, de 312, it 240, fr 227,
pt 130, es 80, nl 80, pl 80, id 54, ko 30); 41 документ с закрашенным полем (у 19 из них закрашенная сумма
исключена из оценки, см. ниже). 13273 значения, 1199 полей с ответом null. (До правок 2026-11-13 этапа 1 —
1574 документа, 13275 значений, 1226 null.) Число документов больше числа независимых: у чека есть варианты `clean` и `photo`, у закрашенного документа —
исходный (`base_doc`). Сколько независимых документов в каждой клетке и какие из них реальные — `../00-plan.md`, раздел 3.

Добавлены 2026-11-11 (сгенерированные, ответы из генератора, найдены в тексте страницы):
- **EuroDocBench** — 625 счетов: по 80 на de, en (en-IE), es, it, nl, pl, pt и 65 на fr. Пять макетов и три
  шрифта, одни и те же для всех языков, — для сравнения языков при прочих равных. Колонка `template` в
  `manifest.csv` — макет/шрифт. Французские счета, у которых шрифт не содержит символа-разделителя разрядов
  (на картинке пустой квадрат), исключены целиком; поэтому у fr 65 счетов и нет моноширинного шрифта.
- **Синтетические чеки** — ещё по 60 независимых чеков de, fr, it (теперь по 80), каждый в вариантах clean и photo.

- `docs/<doc_id>/page_N.png` — страницы в том виде, в каком их получает модель.
- `docs/<doc_id>/answers.json` — правильные ответы по полям:
  - `answer` — ответ в едином виде; `null` — поля в документе нет, правильный ответ модели — null;
  - `printed` — как значение напечатано (для сверки), `masked: true` — значение закрашено.
  - `accepted` (необязательно) — другие верные значения поля: бренд и юр. лицо продавца, дилер/станция,
    другой налоговый номер продавца (Steuernummer, NIPC). Ответ модели верен, если совпал с `answer` или с любым из них;
  - `accept_from` (необязательно) — у счёта напечатана только одна из сумм total_gross / total_net: эта сумма
    засчитывается, в какое бы из двух полей модель её ни записала.
  - `quality: "low"` (необязательно, на уровне документа) — страница плохо читается (низкое разрешение, обрезка,
    неразличимые O/0). Документ оценивается как обычно; отчёты дают точность и с такими документами, и без них.
- `manifest.csv` — по строке на документ: источник, откуда он фактически скачан (`upstream`: id в
  `data/sources.yaml` и путь внутри архива), язык, тип, вариант, закрашенное поле, число значений и null,
  sha256 страниц, основание доверять ответам, `quality` (`low` или пусто).
- `excluded.csv` — что не вошло и почему. Сюда же внесены 60 сумм счёта (total_gross / total_net / total_tax),
  которых нет в документе (ответ был null, поле не закрашено): они удалены из answers.json и не оцениваются.
- `licenses.csv` — лицензия каждого источника с дословной цитатой. У пяти источников (ZUGFeRD, SROIE,
  WildReceipt, KORIE, Bank-Statement-Intelligence) лицензия не установлена явно; они оставлены осознанно:
  документы используются только для локальных замеров и не публикуются.

## Единый вид ответов

| Вид | Формат | Пример |
| --- | --- | --- |
| Дата | `YYYY-MM-DD` | `2015-09-18` |
| Время | `HH:MM`, 24 часа | `13:48` |
| Сумма | десятичное число с точкой, без разделителей разрядов и валюты; сравнивать как число | `889.2`, `27640` |
| Валюта | ISO-код | `EUR` |
| Номер (счёта, налоговый, IBAN) | без печатной подписи («SIRET», «USt-IdNr.») | `20149268321989` |
| Текст (названия) | как напечатано | `COMPTOIR ARIBELLA` |

## Почему ответам можно верить

Значение берётся, только если выполнено одно из условий:

1. оно взято из XML или генератора документа и найдено в тексте самой страницы;
2. страницу целиком просмотрел Claude и подтвердил значение.

Дополнительно его не оспорила независимая проверка (`../reports/review_2026-11-11.md`): если проверка
исправила значение, берётся её исправление.

`null` берётся, только если отсутствие поля подтверждено просмотром страницы. Закрашенные документы берутся, только
если обе проверки согласны, что значение больше нигде не читается.

## Как проверяли

- **Каждое значение** сначала искалось в тексте страницы (текстовый слой PDF и OCR Apple Vision) с учётом форматов
  чисел, дат и переносов строк.
- **Каждое «поля нет» и каждое закрашивание** проверено просмотром всей страницы, уменьшенной примерно до 0,6
  мегапикселя (при таком размере ещё читается мелкий текст счёта A4). Вырезки вокруг поля оказались
  недостаточными: они пропускали повторы значения в других местах страницы (итог прописью, сумма от руки, имя в
  e-mail).
- **Значения с фото и сканов**, которые не нашлись автоматически, досмотрены по полной странице.
- **Независимая проверка** другим агентом: 159 документов целиком, включая все исправленные значения.

Найденные ошибки самих датасетов (исключены из оценки или исправлены):

| Датасет | Ошибка |
| --- | --- |
| InvoiceBenchmark | В разметке суммы без НДС, а напечатаны с НДС |
| ZUGFeRD | Встроенный XML местами расходится с напечатанным PDF; в одном счёте XML описывает другой счёт |
| FATURA | Покупатель и итог под нестандартными подписями не размечены; итог бывает только прописью |
| WildReceipt | Ручная транскрипция с опечатками; итог не размечен, хотя напечатан |
| Португальские чеки | Продавец не размечен; у кредит-ноты записан номер исходного счёта |
| KORIE, SROIE, синтетические чеки | Лишние символы в дате, ошибки распознавания в названии, налоговый номер вместе с подписью |

## Чего здесь нет (сознательно)

- формы XFUND — не бухгалтерия, разметка неоднозначна;
- таблицы (строки счёта, транзакции выписки) — ячейки не проверены поштучно;
- поля, которые не удалось однозначно привести к единому виду (например, даты WildReceipt, где непонятно, что
  стоит первым — день или месяц), — см. `excluded.csv`.

## Известный дефект: порядок дня и месяца в синтетических чеках

Генератор синтетических чеков (`synrec__*`, источник `synthetic_receipts`) печатает дату то как dd/mm, то как
mm/dd, без признака формата на странице; ответ (`answer`) берётся из генератора и верен, но по странице
неоднозначная дата (день и месяц ≤ 12, например «07/04/2024») не отличима от перестановки. Поэтому скорер принимает
оба порядка для неоднозначных дат (правило `date_swap` в `../harness/normalize.py`, решение владельца 2026-11-13 (1)
п. 3). Однозначные даты (день > 12) сравниваются строго. Ответы не менялись; дефект исправить можно только
перегенерацией набора.

## Как собран

Набор собран из промежуточного корпуса скриптом `tools/build_final.py`. И корпус, и скрипт после заморозки удалены;
их код сохранён в git, в коммите-снимке, хэш которого указан ниже. Побайтовая пересборка из исходников не
гарантируется: повторное скачивание источников может дать другие файлы.

Коммит-снимок: см. `git log --grep "Freeze final dataset"`.

Пополнение 2026-11-11 собрано отдельно, скриптами `staging/eurodocbench/build.py` и
`staging/synthetic_receipts/build.py`, и скопировано сюда без изменений (хэши страниц сверены). Проверки и
исключения — `../reports/staging_check.md`. После переноса `staging/` удалена; скрипты, отбор и доказательства
сохранены в git, в коммите `git log --grep "Add EuroDocBench"`.
